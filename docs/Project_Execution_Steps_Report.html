Step 1 Part A: System Design & Microservices Architecture

We designed and implemented a fully decoupled, scalable e-commerce backend by decomposing business domains into 5 independent microservices orchestrated via an API Gateway:

Service Name Port Database Primary Responsibilities
API Gateway :3000 None (Stateless) Reverse proxy routing, Unified Swagger UI (/api-docs), health aggregation, serves Fashion customer UI and Admin portal.
User Service :3001 users.db User registration, profiles, password hashing, role management, address book CRUD.
Product Service :3002 products.db Product catalog, category hierarchy, SKU validation, atomic stock reservation & rollback.
Order Service :3003 orders.db Order placement, order items lifecycle, inter-service inventory reservation with Product Service.
Payment Service :3004 payments.db Simulated multi-channel checkout (UPI, Card, COD), transaction tracking, order status confirmation.
Notification Service :3005 notifications.db Asynchronous event alerts (Email, SMS, in-app notifications) for orders and billing.

Step 2 Part B: Database-per-Service Design

Following strict microservices best practices, no microservice shares a database. Each service owns its private SQLite database file:

Database File Tables Primary Key (PK) & Foreign Keys (FK)
users.db users, addresses users.id (PK, Auto-inc), addresses.id (PK), addresses.user_id (FK -> users.id ON DELETE CASCADE)
products.db categories, products categories.id (PK), products.id (PK), products.category_id (FK -> categories.id), products.sku (UNIQUE)
orders.db orders, order_items orders.id (PK), orders.order_number (UNIQUE), order_items.id (PK), order_items.order_id (FK -> orders.id)
payments.db payments payments.id (PK), payments.transaction_id (UNIQUE), payments.order_id, payments.user_id
notifications.db notifications notifications.id (PK), notifications.user_id, notifications.channel, notifications.status
Step 3 How Microservices Communicate with Each Other (Inter-Service Flow)

Since services are decoupled, they communicate over the local network using RESTful HTTP calls with JSON payloads using the built-in fetch() API.

Primary Example: Order Service (:3003) ➔ Product Service (:3002)

When a customer orders an item, Order Service does NOT touch products.db. Instead:

  1. Verify Item & Price: GET http://localhost:3002/api/products/:id
  2. Atomic Stock Reservation: POST http://localhost:3002/api/products/:id/reserve-stock with { quantity }
  3. Compensating Rollback (Saga Pattern): If any item has insufficient stock, Order Service calls POST http://localhost:3002/api/products/:id/restore-stock to return previously reserved inventory.
// Code from services/order-service/server.js const reserveRes = await fetch(`${PRODUCT_SERVICE_URL}/api/products/${item.product_id}/reserve-stock`, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ quantity: item.quantity }) }); if (!reserveRes.ok) { // Compensating transaction (Rollback) for (const resItem of reservedItems) { await fetch(`${PRODUCT_SERVICE_URL}/api/products/${resItem.product_id}/restore-stock`, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ quantity: resItem.quantity }) }); } return sendError(res, 'Insufficient stock', 400); }

Secondary Example: Payment Service (:3004) ➔ Order Service (:3003)

Once payment is confirmed in payments.db, Payment Service updates Order Service via: PUT http://localhost:3003/api/orders/:id/status with payload { status: "CONFIRMED" }.
